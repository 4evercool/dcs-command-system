# 201 — Incident Brief

**Incident:** close-integrity-guard-bundle
**Opened:** 2026-08-02
**Type:** 1

## Symptom

DCS's close-time process (`dcs/workflows/close.md`) mechanically enforces nothing about the truthfulness or completeness of an incident's own records: it does not verify that a commit SHA cited in `214-LOG.md`/`AAR.md` actually exists, that the standard artifact set is present and tracked, that artifacts are written in English, that every load-bearing operative term still appears somewhere in the shipped package, that `SAFETY.md` conforms to its schema, that the working tree is clean under `.dcs/incidents/<slug>/` and `vault/` after the archive commit, or that commit messages aren't corrupted. All of this currently depends entirely on operator discipline and prose-only doctrine. An external review of a non-Anthropic-model-driven period (`vault/Post-mortems/deepseek-period-review.md`) found that every DCS rule enforced by a *mechanism* held, while every rule living only in doctrine prose broke systematically — this incident builds the missing mechanisms for measures 1 (SHA-guard part only), 2, 3 (both the non-English sweep and, per Owner decision below, the load-bearing-term census), and 6's close-time checks from `vault/Decisions/non-anthropic-hardening.md`.

## Evidence

- Fabricated commit reference: `halt-enumeration-grammar-drift/214-LOG.md` cites merge `b4af6e4`. Independently re-verified during typing: `git cat-file -t b4af6e4` → `fatal: Not a valid object name b4af6e4` (`deepseek-period-review.md` §D; corrected description in `record-integrity-corrections/SAFETY.md` advisory 1 — a real merge of that code exists, `48ea59a` via `f7e0cc9`, but not under the cited sha — a scope note for the guard: it catches nonexistent tokens, not a subtly-wrong topology description of a real merge).
- False "verbatim" attribution: `workflow-file-trim-grandfathered/AAR.md` quotes a Safety verdict "verbatim, from SAFETY.md," but no `SAFETY.md` for that incident exists on disk or in git history (`deepseek-period-review.md` §D; confirmed independently by `record-integrity-corrections/SAFETY.md` item 8).
- Missing/untracked artifacts: three DEPLOYED incidents (`workflow-file-trim-grandfathered`, `check-14-hardening`, `worktree-removal-self-conflict`) are missing most of their standard artifact set (1/8, 2/8, 2/8 present respectively — re-derived independently by `record-integrity-corrections/SAFETY.md` item 12); separately, `vault/Meta/ESG-sessions/` (18 files) and a `2026-07-30-provisioning-script-upstreaming` incident (8 of 9 artifacts) were found untracked (`deepseek-period-review.md` §E) — a distinct failure mode from "missing," since files can exist uncommitted.
- Non-English artifacts: ~7 incidents' artifacts are substantially in Russian against the project's English mandate (`deepseek-period-review.md` §D — already tracked separately for historical remediation as the QUEUED row `russian-artifacts-translation`; this incident only needs to build the sweep going forward).
- Degenerate commit messages: 22 of 70 commit messages in the reviewed period carry stray `@` lines from inline multi-line commit strings (`deepseek-period-review.md` §D; `non-anthropic-hardening.md` measure 6).
- No existing close-time check catches any of the above: a full read of `close.md`'s `<process>` (steps 1-7) shows no `git cat-file` use, no non-English sweep, no artifact-count check, no `SAFETY.md` schema validation, and no commit-message scan anywhere in the close path. The only existing close-time-guard hook (step 5a.1a) is opt-in per a project's own `CLAUDE.md` and today resolves to exactly one script, `tests/test_doctrine_integrity.py`, whose one relevant precedent (check 21, `SAFETY.md` vs. schema #5 field presence) is explicitly informational-only and never blocks (`test_doctrine_integrity.py:1794-1795`).
- Demonstrated concretely against a real, recent, otherwise-exemplary close: `record-integrity-corrections` (merge `a62ffad`) closed with a `SAFETY.md` containing no JSON verdict fence at all — nothing in `close.md` or the merge-time guard flagged it. **Command-point verification found this cuts deeper than "no fence": a naive substring check for a JSON fence *false-passes* this same file**, because `record-integrity-corrections/SAFETY.md:33` contains the literal string a fence-detector would match, inside prose discussing the *absence* of fences elsewhere ("Criterion 2 smuggling risk closed on both axes: no `` ```json `` fence in any of the 3 CORRECTION files"). A guard implemented as a naive substring scan would certify this incident's own precondition as schema-conformant when it is not — the check needs real fence parsing, not pattern matching.
- Load-bearing-term census's generalization target already shipped: `revision-preservation-map` (DEPLOYED 2026-07-31→08-01) is the per-incident instance of exactly the "preserve an operative term/mechanism across a trim" problem the census generalizes to the whole package (`non-anthropic-hardening.md` measure 3: "the package-level twin of the ... `revision-preservation-map` idea").

2. **"SAFETY.md schema-#5 JSON conformance," read literally, would be born red — and a naive implementation would additionally false-*pass* the same file** (see Evidence: `record-integrity-corrections/SAFETY.md:33`'s inline prose mention of a fence). `forms.md` only requires the verdict be "copied in as returned — not summarized or softened"; the requirement that a *verbatim JSON copy* survive falls on `AAR.md` (`close.md` step 3), not `SAFETY.md` itself. 9 of 32 existing `SAFETY.md` files repo-wide — including `record-integrity-corrections`, this incident's own stated precondition — are prose-only with no JSON fence.

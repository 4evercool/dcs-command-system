## Execution mode

**Sequential in two waves, with an IC step between them** — not plain parallel,
which is why this 203 is written rather than skipped.

```
Wave 1:  S1 alone            (.gitattributes)
   ↓
IC STEP: path-scoped working-tree re-materialisation
         (not a tasking — see below)
   ↓
Wave 2:  S2 ‖ S3 ‖ S4        (territories disjoint by file)
```

**Why the IC step is not a tasking.** Both chiefs concluded independently that
the re-materialisation cannot be delegated: it crosses every territory line (the
only honest glob is `**/*`, which is the absence of a territory), it is invisible
to `dcs_gate.py` because it is neither an Edit nor a Write, it destroys
uncommitted work, and it touches `.dcs/**` which is barred to specialists by
construction. It is one IC act, run between the waves.

**Why Wave 1 precedes it and Wave 2 follows it.** The IC resolved the chiefs'
ordering conflict on measured fact: **83 files in this worktree are `w/crlf`, 54
of them in shipped scope**, so S3's new no-CRLF check is red until the tree is
re-materialised — a specialist could not deliver green evidence for its own
tasking. The Logistics Chief's counter-reason (the gate invariant must exist
first) was ruled void by its own measurements: the re-materialisation is not an
Edit or Write, so the old gate never adjudicates it, and this incident's own
`IAP.md` / `IAP-APPROVED` are untracked and pure LF, so no census change can move
the stamp.

**Struck from the Logistics plan by IC directive:** Stage 4 (a separate
renormalise commit — measured to be a no-op, the index is already all-LF) and
Stage 6 (a mid-incident live-hook swap in `C:\DCS` — the merge at close
propagates it instead).

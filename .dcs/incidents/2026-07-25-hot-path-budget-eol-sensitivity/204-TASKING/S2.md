### (3) THEN patch `dcs/hooks/dcs_gate.py`

Replace `sha256_of` with `approval_digests(path)` returning the **deduped list**
of sha256 hex digests of three byte forms:

- `raw` — the file as-is
- `lf = raw.replace(b'\r\n', b'\n')`
- `crlf = lf.replace(b'\n', b'\r\n')` — **derive from `lf`, never from `raw`**,
  or existing CRLF doubles into `\r\r\n`

`marker_valid` becomes `stored_hash in approval_digests(iap)`.

**Fold only `\r\n`. Leave a lone `\r` untouched in all three forms**, and say so
in the docstring with the reason: two files differing by a real CR must still
hash apart. The equivalence class widens by exactly the git text-conversion the
policy declares and not one byte more.

Leave the `utf-8-sig` read of `IAP-APPROVED` alone — that tolerance is on the
*stamp file*, not the hashed file, and the BOM family is out of scope.

Update the module docstring's step 5 to say the marker matches the IAP's content
**modulo line-ending representation**, not its exact bytes.

**Why a two-member set {raw, lf} is not enough** (IC-verified): with a legacy
CRLF stamp it still denies on an LF disk file and allows on a CRLF one — the
verdict changes with the representation, which is precisely what criterion 4
forbids. The synthesised `crlf` member is what closes it.

## Environment trap — read this

**Authoring `b'\r\n'` literals through a bash heredoc silently converts the
escapes into real control characters**, producing a `SyntaxError` — and
`dcs_gate.py` **fails open** on error, so the resulting "allow" looks like a
passing test. The Planning Chief lost a cycle to this. **Author those literals
with the Write/Edit tool.**
